# Правила интеграционного тестирования на Python

## 1. Цель интеграционного теста

Интеграционный тест проверяет взаимодействие реальных компонентов и внешний контракт: HTTP, PostgreSQL, брокеры, авторизацию, фоновые операции, взаимодействия сервисов. Не превращай такой тест в unit-тест из моков внутренних вызовов. Моки допускаются лишь для зависимостей вне тестируемой границы (например, стороннее API или недоступный/платный сервис).

## 2. Формат тестов

- Предпочитай pytest для новых тестов и принятый стиль существующего репозитория.
- Имена тестов должны отражать **сценарий и ожидаемое поведение** (`test_create_note_rejects_foreign_space`), а не `test_create_note_1`.
- Один тест — один логически целостный сценарий. Несколько assertions допустимы, если они проверяют один контракт.
- Проверяй наблюдаемые результаты: ответы API, записи в БД, доставленные сообщения, состояние очереди, отсутствие запрещённых эффектов.
- Используй `@pytest.mark.parametrize` для общего контракта с разными входами; задавай `id` для осмысленных случаев. Не создавай мегатесты с ветками `if` по сценарию.
- Отделяй проверки функционального поведения от проверок подготовки окружения; падение фикстуры должно быть диагностируемо.

## 3. Fixtures и управление ресурсами

- Используй pytest-фикстуры для создания клиентов, авторизации, тестовых данных, временных каталогов и очистки.
- `scope` минимально необходимый: `function` для изменяемых ресурсов, более широкие scope — только для действительно общих безопасных объектов.
- `autouse=True` — только при ясной необходимости; скрытые сетевые вызовы и пересоздание БД в autouse запрещены.
- Для очистки используй `yield`/`request.addfinalizer` и проектные механизмы удаления. Ресурс должен оставаться отслеживаемым даже при падении assertion.
- Не удаляй всю тестовую БД или чужие записи вместо удаления данных текущего теста без отдельного изолированного окружения и явного разрешения.
- Если создание ресурса завершилось частично, предусмотрите компенсацию/сбор диагностик. Cleanup не должен безмолвно скрывать главный сбой.
- Не делай тесты зависимыми от порядка выполнения или результатов других тестов.

## 4. Тестовые данные и изоляция

- Данные должны иметь уникальный префикс/ID запуска там, где используется общая среда.
- Фабрики данных — для осмысленных повторяющихся объектов; избегай универсальных Builder со множеством флагов и скрытыми побочными эффектами.
- Тесты должны допускать повторный запуск; `ON CONFLICT`/upsert уместен лишь если он сохраняет проверяемый контракт.
- Не предполагай, что транзакционный rollback одного соединения откатит изменения, сделанные другим сервисом или соединением.
- Разделяй seed данные и объекты, созданные конкретным тестом. Очистка не должна затрагивать чужие данные.
- Для тестов с конкурентностью/параллельным CI учитывай независимость namespace, таблиц, очередей и пользователей.

## 5. HTTP, БД, брокеры и eventual consistency

- Проверяй конкретный контракт: статус ответа **и** значимое содержимое/побочный эффект.
- Используй явные таймауты сетевых операций; не оставляй бесконечное ожидание.
- Для БД проверяй состояние через существующий test helper или запросы, а не детали внутренних вызовов сервиса.
- Для брокера проверяй идентификатор, содержимое и количество релевантных сообщений, а также отсутствие лишних — если это часть контракта.
- При асинхронном результате предпочитай polling по состоянию с монотонным deadline (`time.monotonic()`), разумным интервалом и диагностикой последнего наблюдения. Не используй произвольный `time.sleep(5)` как механизм ожидания.
- Поллинг не должен повторно создавать ресурс или выполнять разрушающее действие.
- Retry тестового API не должен скрывать дефекты приложения: повторяй только чтение состояния или обоснованно идемпотентную операцию, а не весь тест.
- Для таймаутов и backoff в unit-тестах test helpers используй fake clock; в интеграции измеряй реальные условия с запасом к CI.

## 6. Проверки и diagnostics

- Используй обычные `assert` pytest; его assertion rewriting даёт хорошую диагностику. Не заменяй их `unittest.TestCase` или кастомными assert wrappers без причины.
- Утверждения должны быть конкретными: `assert response.status_code == 201`, `assert payload["id"] == expected_id`.
- Не дублируй алгоритм реализации при вычислении expected — используй фиксированные сценарии/договорённости контракта.
- Проверяй негативные случаи: неверные права, отсутствующий объект, некорректный ввод, повторы, падения зависимостей, частичные ошибки — по ответственности сценария.
- Для опасных операций проверяй *отсутствие* незапланированных эффектов, например данные другого пользователя не изменены.
- Если response содержит секреты, не вставляй их в assertion messages и логи; редактируй диагностику.
- Не используй `assert condition is True`, когда можно проверять более конкретное значение/структуру.

## 7. Mocks и границы

- Не мокай внутренние API сервиса, если цель — проверить интеграцию.
- Для unit-тестов test helpers/клиентов допустимы `Mock`, `autospec`, `monkeypatch`, fake transport; подменяй только границы и фиксируй ожидаемое поведение.
- Не требуй `expect` внутри таблицы автоматически: это соглашение обсуждалось для Go сгенерированных моков; в Python следуй принятым фикстурам, pytest parametrization и конкретному mock API проекта.
- Избегай огромного набора произвольных `Mock`, через который тест не проверяет реальную интеграцию.

## 8. Маркеры и запуск

- Различай быстрые проверки, интеграционные и потенциально разрушительные/долгие сценарии через проектные маркеры/команды.
- `pytest.mark.skip/xfail` допустимы только с ясной причиной и сроком/условием пересмотра. Не добавляй их для маскировки регрессий.
- Прежде чем запускать тесты, проверь профиль окружения, переменные и отсутствие prod-адресов; неизвестное окружение должно приводить к безопасному отказу, а не выбору prod.
- Не добавляй произвольно `pytest-xdist` и конкурентный запуск: убедись, что фикстуры и сервисы изолированы.

## 9. Качество unit-тестов вспомогательной инфраструктуры

- Самостоятельно тестируй загрузку конфигурации, фабрики, serializers, API wrappers и retry-логику, если она нетривиальна.
- Для файлов используй `tmp_path`; для времени — подмену часов; для ошибок транспорта — fake/`autospec`.
- Проверяй и успех, и ошибки, но не смешивай независимые контракты в один тест.
- Не создавай синтетические архитектурные слои только ради тестируемости простого helper.

## 10. Работа с SQL-фикстурами

- SQL-данные должны быть воспроизводимыми; выбирай явный порядок загрузки зависимостей.
- Не удаляй существующие записи без запроса. Seed-операции и миграции разделяй.
- Для генерации тестовых данных допускаются SQL-файлы рядом с тестами, если такой формат уже принят.
- Проверяй, какие операции выполняются вне транзакции и какие данные переживают тест.
- Не раскрывай DSN/пароли при исключении и логировании.

## 11. Перед коммитом

Проверь Makefile/CI и используй принятые команды (`make lint`, `make test`, если присутствуют и безопасны), затем соответствующие тесты. Падающие проверки не «лечатся» удалением assertions, изменением ожидаемых данных, глушением линтера, необоснованным `skip` или массовым рефакторингом. Если окружение недоступно, отчитайся о блокере, не объявляй полный успех.

## 12. Гарантированная очистка тестовых ресурсов

1. Каждый интеграционный тест, создающий ресурсы во внешних системах, должен предусматривать их очистку.
2. Регистрируй очистку ресурса как можно раньше — до проверок, способных прервать выполнение теста.
3. Если ресурс может быть создан без получения успешного ответа, предусматривай способ обнаружить и очистить его после частичного сбоя.
4. По возможности используй уникальные идентификаторы или маркеры тестовых ресурсов.
5. Используй pytest-фикстуры с `yield`, `request.addfinalizer()` или контекстные менеджеры для управления жизненным циклом ресурсов.
6. Учитывай, что код после `yield` в фикстуре не выполнится, если ошибка произошла до достижения `yield`. Для поэтапного создания ресурсов регистрируй финализаторы после успешного создания каждого ресурса.
7. Очистка должна быть безопасной при повторном выполнении, если это возможно.
8. Не удаляй ресурсы, принадлежность которых текущему тесту не подтверждена.
9. Не скрывай ошибки очистки без причины: они могут указывать на загрязнение тестового окружения.
10. Проверяй сценарии частичного выполнения, повреждённых ответов и сетевых ошибок, если они способны оставить ресурсы в окружении.

**Главный принцип:** тест должен освобождать созданные им ресурсы даже в случае падения assertions, ошибок обработки ответа или частичного выполнения внешней операции.

### 13. Проверка сохранения и очистки данных

1. Если тест проверяет сохранение данных, не ограничивайся успешным ответом операции записи.
2. Проверяй результат независимой операцией чтения через предусмотренный контракт системы.
3. Не требуй повторного чтения автоматически от всех тестов, проверяющих только HTTP-контракт.
4. Регистрируй очистку внешнего ресурса до операций, которые могут завершиться ошибкой после его фактического создания, если известен безопасный способ обнаружения ресурса.
5. По возможности используй уникальные идентификаторы тестовых данных, известные до выполнения запроса.
6. Не предполагай, что неуспешный HTTP-запрос означает отсутствие побочного эффекта на сервере.
7. При асинхронном сохранении используй ограниченное ожидание доступности данных с таймаутами отдельных запросов.
8. Если надёжная очистка после потери ответа невозможна, используй изоляцию тестового окружения или документируй ограничение.
9. Не добавляй в API специальные механизмы для тестов без согласования архитектурных изменений.
10. Не усложняй тест дополнительными проверками, которые не относятся к его контракту.
