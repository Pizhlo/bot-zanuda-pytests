# Git workflow и требования к коммитам

## Перед изменением кода

1. Выполни `git status --short --branch` и убедись, что видишь текущую ветку и локальные изменения.
2. Уточни у пользователя: **«Текущая ветка <имя> — правильная для задачи BZ-<номер>, или нужно создать новую от main?»** Не начинай изменения до получения ответа: ветка могла остаться от прошлой задачи.
3. Если необходимо создать ветку, проверь отсутствие незакоммиченных изменений, актуальность `main` и целевой remote. Не выполняй `reset --hard`, force push, `stash`, `rebase` или очистку файлов автоматически.
4. Создавай `BZ-123` либо `BZ-123-краткое-описание` по принятому в репозитории соглашению. Не используй `main` для разработки фичи.

Пример безопасного сценария **после подтверждения пользователя и при чистом дереве**:

```bash
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c BZ-123
```

Это шаблон, а не команда для безусловного запуска: ветка, remote и права доступа могут отличаться.

## В процессе работы

- Не изменяй чужие файлы, комментарии, настройки и тесты без связи с задачей.
- Не совмещай нерелевантные рефакторинги с фичей.
- Не переписывай историю, не делай force push без разрешения.
- Сохраняй логически связанный объём изменений в одном коммите; отдельные самостоятельные шаги могут быть разными коммитами, и каждый из них должен проходить проверки.

## Проверки перед коммитом

ИИ обязан проверять именно ту версию кода, которая попадёт в коммит.

1. Заверши изменения, относящиеся к текущему коммиту.
2. Добавь необходимые файлы и изменения в Git index.
3. Проверь `git diff --cached` и убедись, что подготовленные изменения соответствуют задаче.
4. Убедись, что проверяемые файлы в рабочем дереве совпадают с версиями в индексе.
5. Если рабочее дерево содержит дополнительные изменения, способные влиять на проверки, не считай запуск тестов в нём подтверждением корректности подготовленного коммита.
6. При частичном staging проверяй код в отдельном изолированном рабочем дереве, созданном из содержимого Git index, либо согласуй включение необходимых изменений в коммит.
7. Выполни `make lint` и `make test` для версии кода, соответствующей подготовленному коммиту.
8. После проверок не изменяй содержимое коммита без повторной проверки.
9. Перед созданием коммита ещё раз проверь подготовленные изменения.
10. Не создавай коммит, если его содержимое не прошло обязательные проверки.

### Безопасность

- Не выполняй `git reset --hard`, `git clean`, `git stash` или другие команды, способные затронуть пользовательские изменения, без согласования.
- Не добавляй посторонние файлы в коммит только ради прохождения проверок.
- Не изменяй чужие незакоммиченные изменения.
- Если проверить подготовленный коммит безопасно невозможно, сообщи о проблеме и запроси решение.

Успешный запуск тестов в рабочей директории не считается достаточным подтверждением, если её содержимое отличается от проверяемого снимка коммита.

Правильно:

- `BZ-123: добавлены проверки повторной доставки сообщений`
- `BZ-123: исправлена очистка тестовых данных`
- `BZ-123: переработаны фикстуры PostgreSQL`

Неправильно:

- `BZ-123: добавить тесты`
- `BZ-123: fix tests`
- `update`.

## Если проверки невозможно запустить

Не скрывай проблему, не подменяй тесты моками без согласования, не изменяй CI ради прохождения. Укажи точную причину (нет тестового окружения, права, внешняя зависимость) и перечень реально выполненных локальных проверок. Обязательное требование успешных проверок означает, что неподтверждённое изменение нельзя представлять как готовый проверенный коммит.

## Границы изменений

- Коммит должен содержать изменения по заявленной задаче и непосредственно необходимые тесты/документацию.
- Не добавляй в коммит посторонние рефакторинги и исправления найденных по пути дефектов без согласования.
- Если посторонний дефект мешает проверкам, сообщи об этом до исправления и запроси решение.
- После согласования отдельного исправления используй согласованную задачу и соответствующую ветку/коммит; не придумывай новый BZ-ID.
