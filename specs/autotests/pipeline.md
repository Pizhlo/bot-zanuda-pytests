# Пайплайн тестов auth-service

Окружением управляет testkit, подключённый сабмодулем на конкретном коммите.
Поддерживается только Linux. `make integration-run` готовит инфраструктуру, ждёт
готовности auth-service после его собственных миграций схемы,
выполняет `make test-auth-service` с фикстурой данных и завершает прогон.
`integration-up` заканчивается до загрузки данных и pytest, оставляя контейнерный стенд для ручных этапов.
В AUTH_MODE=host integration-run работает с уже запущенным сервисом без пересоздания
зависимостей. Готовые конфиги лежат в Git, порты постоянные, RUN_ID локально не требуется.
Повторный host-run разрешён; SEED_DATA=false явно пропускает seed только локально.

## Контракт тестовых данных

Перед tests/auth_service сессионная autouse-фикстура вызывает общий загрузчик SQL.
Make test-data-auth-service-up вызывает его же через python -m tools.seed_auth без pytest.
Все up-файлы testdata/auth-service применяются в порядке имени одной транзакцией.
ON CONFLICT обновляет фиксированные тестовые записи, остальные строки не затрагивает.
Ошибка SQL откатывает весь набор и блокирует тесты. Базовые записи остаются для IDE;
временные ресурсы сценариев очищаются их фикстурами.

PYTEST_CONFIG задаёт YAML (default config.yaml), TESTDATA_PATH — другой каталог SQL,
TESTDATA_DATABASE_URL — явную БД. Нужен Python/psycopg из uv.lock; CLI migrate не нужен.
История версий данных не используется; старую таблицу код не читает/не удаляет.
SEED_DATA=false пропускает фикстуру только локально; явная команда seed применяет данные.

## Версии и результат

Локальный запуск и CI этого репозитория собирают тесты и SQL из текущих исходников.
Образ auth-service по умолчанию latest; AUTH_IMAGE переопределяет его.
CI сервиса использует свою сборку приложения с опубликованным тегом тестов
(по умолчанию latest).

Полный локальный контейнерный успех удаляет контейнеры и тома прогона и выводит результат pytest
без файлов отчётов. Ошибка сохраняет окружение и `.logs/<run-id>/run.log`.
В CI вывод подготовки, pytest и Docker попадает в журнал GitHub Actions;
попытка уборки выполняется при любом исходе. Сервер отчётов и загрузка артефактов не нужны.
При AUTH_MODE=host (в том числе integration-run), отдельных командах и запуске pytest
из IDE окружение удаляет разработчик через containers-down из auth-service. Процесс IDE не останавливается.

## Локальное окружение потребителя (актуальное уточнение)

AUTH_MODE=host использует уже запущенный сервис с config.yaml из auth-service;
зависимости готовит containers-up, останавливает containers-down этого репозитория.
Тесты/seed читают pytests/config.yaml либо PYTEST_CONFIG (относительно потребителя).
При host/host seed и pytest выполняются без Docker; отдельная диагностика/уборка
ранее созданных контейнерных jobs может обращаться к Docker. Seed использует общий Python-загрузчик.
Отдельные host seed/test не требуют integration-up; данные готовит фикстура pytest.
Пользовательские конфиги не изменяются. CI и полный контейнерный цикл сохраняются.


## Подготовка данных фикстурой (актуальный контракт)

Для auth-service сессионная autouse-фикстура выполняет все testdata/auth-service/*.up.sql
через psycopg одной транзакцией. ON CONFLICT по фиксированным тестовым ключам позволяет
повторный запуск; другие записи не затрагиваются. Базовый набор остаётся для IDE,
временные ресурсы отдельных тестов очищаются их фикстурами. SEED_DATA=false локально
пропускает подготовку; CI требует true. Прямая make test-data-auth-service-up использует
тот же загрузчик без запуска pytest. CLI migrate и история версий тестовых данных
не используются. Миграции схемы выполняет только auth-service.


## Когда запускается workflow «Тесты»

Автоматически — на push в main/develop и PR в эти ветки, если изменены:

- `tests/auth_service/**`, `parameters/auth_service/**`, общий `parameters/__init__.py`,
  общие `tests/fixtures/**`,
  conftest и `tests/__init__.py`;
- `src/**`, `utils/**`, `testdata/auth-service/**` или загрузчик `tools/seed_auth.py`;
- зависимости и настройки pytest/Python, Makefile, Dockerfile или .dockerignore;
- закреплённая версия testkit, .gitmodules или .github/workflows/auth-service.yaml.

Изменения только README/спецификаций или `tests/webserver/**` этот workflow не запускают.
В PR учитывается весь diff ветки: если он уже содержит auth-изменения, добавление
коммита только с README всё равно запускает проверку. Ручной Run workflow доступен всегда.
Единый список путей находится в `paths: &auth_service_paths` этого workflow; при добавлении
зависимостей тестов обновляйте его. Список для pull_request ссылается на него через `*auth_service_paths`.

Интеграционное задание пропускается для PR из fork: такому запуску недоступны
Actions Secrets и приватный testkit. Условие действует до checkout; это пропуск,
а не успешное выполнение тестов. PR из веток этого репозитория и ручные запуски
сохраняют прежнее поведение. Secrets внешнему PR не передаются.


## Уточнения после аудита runner

Наличие state.json не подтверждает владение Docker-проектом: повторный up после
конфликта имени снова отказывает, а down не удаляет отвергнутые ресурсы.
Для IDE настройка RabbitMQ принадлежит containers-up; integration-rabbitmq-setup
не обращается к Docker и объясняет этот способ. После смены TEST_MODE на host
сохранённые контейнеры pytest/seed доступны через logs/down до явной уборки.

TESTDATA_PATH и TESTDATA_DATABASE_URL работают также в контейнерных seed/pytest.
Integration-команды разрешают SQL-каталог относительно INTEGRATION_ROOT и монтируют
его read-only по отдельному пути. Без override используются SQL образа. Неверный
каталог останавливает подготовку до Docker/БД; его удаление не блокирует logs/down.
DSN не меняет конфигурацию HTTP-клиентов и сервиса. Параметры применяются к текущей команде.

Ранние отказы параметров/инициализации получают отдельный initialization.log в
.logs/<run-id>, не затрагивающий активный прогон. Небезопасный RUN_ID заменяется
именем initialization только для диагностического каталога; CI использует журнал job.


## Пайплайн webserver (BZ-206)

Для webserver выбирается INTEGRATION_SERVICE=webserver; WEBSERVER_MODE и TEST_MODE
поддерживают host/host, host/container, container/host и container/container на Linux.
Команды integration-* сохраняют общий lifecycle testkit. Containers-up/down из
webserver управляют зависимостями IDE; runner не останавливает процесс и эти ресурсы.
Host/host seed/pytest не требуют Docker или предварительного integration-up.

PostgreSQL, Redis и RabbitMQ готовятся перед схемой из закреплённого docker-коммита.
Явный манифест исключает эксплуатационную миграцию Sequin 000014. Повторная подготовка
сохраняет данные, изменение применённого набора требует адресного пересоздания стенда.
Webserver не выполняет миграции сам. После схемы и readiness фикстура атомарно готовит
SQL testdata/webserver из версии тестов. Standalone test-data-webserver-up использует
тот же loader без pytest. Базовые данные остаются для IDE; SEED_DATA=false только локально.
Очередь notes очищается до запроса каждого теста и после сценария; ожидание ограничено
по времени. Проверяются health, metrics и все существующие notes-параметры.

CI webserver: PR в main, workflow_dispatch и workflow_call; образ текущего коммита и
опубликованные тесты AUTOTESTS_TAG=latest либо явный тег. Публикация сервиса независима.
CI pytests: push/PR main/develop с фильтрами связанных webserver/common/SQL/build файлов
и testkit gitlink; ручной запуск без diff с override webserver_image. Он использует
текущие тесты и данные с опубликованным сервисом. Старый выключенный test.yaml заменяется.
Fork PR пропускается до доступа к приватным зависимостям. Секреты содержат только
настройки доступа/образов; готовые тестовые YAML не генерируются из Secrets.

CI использует уникальный RUN_ID без host-портов, показывает версии и реальные сводки,
собирает логи перед always cleanup. Успешный локальный container-run убирает свои
ресурсы, ошибка сохраняет стенд и логи; IDE-инфраструктура всегда остаётся пользователю.
Пользовательские config.yaml не изменяются; PYTEST_CONFIG выбирает конфиг seed/pytest.
Состояние webserver отделено от auth; прежний auth-контракт остаётся неизменным.

## Единый запуск окружения

Testkit — единственный способ подготовки автоматизированного тестового окружения.
Корневой docker-compose.yaml и команды start/stop/restart/clean-containers удалены.
Используйте integration-up/run/logs/down с выбранным INTEGRATION_SERVICE;
зависимости IDE запускаются containers-up в репозитории сервиса. Прямой pytest
и отдельные test/seed команды сохранены. Общий make test описан ниже.
Локальный .env и config.yaml не удаляются: .env также используется для IMAGE_NAME
при сборке/публикации образа. Старые CI Secrets удаляются отдельно после миграции main.


## Общий запуск всех сервисов

`make test` собирает текущий checkout pytests один раз и последовательно запускает
наборы auth-service и webserver в двух отдельных контейнерных стендах testkit.
Каждому стенду назначается уникальный RUN_ID; порты хоста не публикуются.
Используются встроенные конфиги и SQL образа, SEED_DATA=true. Локальные режимы,
PYTEST_CONFIG, TESTDATA_PATH/TESTDATA_DATABASE_URL и пользовательский RUN_ID
не переопределяют этот изолированный запуск. AUTH_IMAGE/WEBSERVER_IMAGE позволяют
выбрать образы сервисов; по умолчанию используются опубликованные latest.
Оба набора запускаются даже при ошибке первого. Общая ошибка сборки блокирует оба.
Логи сохраняются в .logs/<общий-id>/; итог содержит статус каждого сервиса.
Любая ошибка тестов, подготовки, логирования или уборки даёт ненулевой exit code.
При любом исходе выполняется попытка удалить только ресурсы текущего запуска;
при Ctrl+C/SIGTERM выполняется уборка активного стенда, второй набор не запускается.
SIGKILL не позволяет гарантировать уборку. Команды test-auth-service/test-webserver
остаются прямым pytest по готовому окружению; integration-run сохраняет свой контракт.
