# Пайплайн тестов auth-service

Окружением управляет testkit, подключённый сабмодулем на конкретном коммите.
Поддерживается только Linux. `make integration-run` готовит инфраструктуру, ждёт
готовности auth-service после его собственных миграций схемы,
выполняет `make test-auth-service` с фикстурой данных и завершает прогон.
`integration-up` заканчивается до загрузки данных и pytest, оставляя контейнерный стенд для ручных этапов.
В AUTH_MODE=host integration-run работает с уже запущенным сервисом без пересоздания
зависимостей. Готовые конфиги лежат в Git, порты постоянные, RUN_ID локально не требуется.
Повторный host-run разрешён; SEED_DATA=false явно пропускает seed только локально.

## Контракт тестовых данных

Перед tests/auth_service сессионная autouse-фикстура вызывает общий загрузчик SQL.
Make test-data-auth-service-up вызывает его же через python -m tools.seed_auth без pytest.
Все up-файлы testdata/auth-service применяются в порядке имени одной транзакцией.
ON CONFLICT обновляет фиксированные тестовые записи, остальные строки не затрагивает.
Ошибка SQL откатывает весь набор и блокирует тесты. Базовые записи остаются для IDE;
временные ресурсы сценариев очищаются их фикстурами.

PYTEST_CONFIG задаёт YAML (default config.yaml), TESTDATA_PATH — другой каталог SQL,
TESTDATA_DATABASE_URL — явную БД. Нужен Python/psycopg из uv.lock; CLI migrate не нужен.
История версий данных не используется; старую таблицу код не читает/не удаляет.
SEED_DATA=false пропускает фикстуру только локально; явная команда seed применяет данные.

## Версии и результат

Локальный запуск и CI этого репозитория собирают тесты и SQL из текущих исходников.
Образ auth-service по умолчанию latest; AUTH_IMAGE переопределяет его.
CI сервиса использует свою сборку приложения с опубликованным тегом тестов
(по умолчанию latest).

Полный локальный контейнерный успех удаляет контейнеры и тома прогона и выводит результат pytest
без файлов отчётов. Ошибка сохраняет окружение и `.logs/<run-id>/run.log`.
В CI вывод подготовки, pytest и Docker попадает в журнал GitHub Actions;
попытка уборки выполняется при любом исходе. Сервер отчётов и загрузка артефактов не нужны.
При AUTH_MODE=host (в том числе integration-run), отдельных командах и запуске pytest
из IDE окружение удаляет разработчик через containers-down из auth-service. Процесс IDE не останавливается.

## Локальное окружение потребителя (актуальное уточнение)

AUTH_MODE=host использует уже запущенный сервис с config.yaml из auth-service;
зависимости готовит containers-up, останавливает containers-down этого репозитория.
Тесты/seed читают pytests/config.yaml либо PYTEST_CONFIG (относительно потребителя).
При host/host Docker runner не вызывается; seed использует общий Python-загрузчик.
Отдельные host seed/test не требуют integration-up; данные готовит фикстура pytest.
Пользовательские конфиги не изменяются. CI и полный контейнерный цикл сохраняются.


## Подготовка данных фикстурой (актуальный контракт)

Для auth-service сессионная autouse-фикстура выполняет все testdata/auth-service/*.up.sql
через psycopg одной транзакцией. ON CONFLICT по фиксированным тестовым ключам позволяет
повторный запуск; другие записи не затрагиваются. Базовый набор остаётся для IDE,
временные ресурсы отдельных тестов очищаются их фикстурами. SEED_DATA=false локально
пропускает подготовку; CI требует true. Прямая make test-data-auth-service-up использует
тот же загрузчик без запуска pytest. CLI migrate и история версий тестовых данных
не используются. Миграции схемы выполняет только auth-service.


## Когда запускается workflow «Тесты»

Автоматически — на push в main/develop и PR в эти ветки, если изменены:

- tests/auth_service/** (имя каталога с подчёркиванием), общие tests/fixtures/**,
  conftest и tests/__init__.py;
- src/**, utils/**, testdata/auth-service/** или загрузчик tools/seed_auth.py;
- зависимости и настройки pytest/Python, Makefile, Dockerfile или .dockerignore;
- закреплённая версия testkit, .gitmodules или .github/workflows/auth-service.yaml.

Изменения только README/спецификаций или tests/webserver/** этот workflow не запускают.
В PR учитывается весь diff ветки: если он уже содержит auth-изменения, добавление
коммита только с README всё равно запускает проверку. Ручной Run workflow доступен всегда.
Единый список путей находится в paths: &auth_service_paths этого workflow; при добавлении
зависимостей тестов обновляйте его. Список для pull_request ссылается на него через *auth_service_paths.
